# Grilled Heads-Up

A personal calendar and to-do app that links Tasks to the Events they prepare for, and warns when an Event is At risk. It ships as an installable PWA (Android/Chrome first) with a small Node + SQLite server.

- What it is and why: [docs/Konzept.md](docs/Konzept.md), [docs/v1-scope.md](docs/v1-scope.md)
- Domain terms (use these in code): [CONTEXT.md](CONTEXT.md)
- Decisions: [docs/adr/](docs/adr/)

## Layout

```
client/   React + Vite PWA (TypeScript). Tasks, Events, Lists, Tags and Subtasks live in the browser's IndexedDB and sync through the server.
server/   Node + Express server: serves the built PWA, owns the SQLite file (sign-in, sync).
e2e/      Playwright end-to-end tests, run against the built app served by the server.
tools/    The security gates of CI as tested code: the allowlist of exceptions, the npm audit and CodeQL gates, the ignore files for Trivy and gitleaks, the check for skipped tests.
```

npm workspaces; run every command below from the repo root.

## Requirements

- Node 22 (see `.nvmrc`)
- Docker with Compose, for the container

## Run

**Everything in Docker (one command):**

```sh
docker compose up --build
```

Open http://localhost:3000. The SQLite file lives in the `data` volume at `/data/grilled-heads-up.sqlite`. Set `PORT=8080` in front of the command to use another port.

**Without Docker:**

```sh
npm install
npm run build   # builds client and server
npm start       # http://localhost:3000, SQLite file in ./data/
```

**While developing the UI:**

```sh
npm run build && npm start   # once, in a second terminal: the API, incl. sign-in
npm run dev                  # Vite dev server with hot reload, http://localhost:5173
```

The dev server passes `/api` on to the server at port 3000. The service worker only runs in the built app, so check offline behaviour with `npm run build && npm start`.

### Sign in

The app opens with a sign-in screen (ADR-0006). On first launch, *Create passkey* registers a passkey and makes you the **Owner**; the app then shows a **Recovery code** once, to print or store. After that, nobody else can register: more passkeys (e.g. for a laptop that doesn't share Google Password Manager) are added with *Add a passkey* at the bottom of the home screen, while signed in. If no passkey is at hand, the recovery code signs you in, shows its replacement once (each use spends the code) and offers to create a passkey. *New recovery code* replaces a code that got lost. Passkeys must check who holds them (fingerprint, face or screen lock); a security key that only senses a touch is refused.

A device that was signed in keeps working offline (its data is on the device); the server checks the session again when it can be reached. Passkeys only work on `localhost` or HTTPS, and are bound to the address the app is opened at (see `ORIGIN` below).

### Install on an Android phone

The PWA needs HTTPS (or `localhost`) to be installable. To try it on a phone during development, forward the port over USB (`chrome://inspect` → *Port forwarding* → `3000` → `localhost:3000`), open `http://localhost:3000` in Chrome on the phone and choose *Install app*. The app then starts from its home-screen icon without browser UI and works in airplane mode.

## Test

```sh
npm test                    # unit tests, then end-to-end tests
npm run test:unit           # Vitest in client, server and tools, with coverage (thresholds fail the run)
npm run test:e2e            # builds, starts the servers, runs Playwright on an emulated Pixel 7
npm run test:mutation       # Stryker mutation tests of client, server and tools, every source file by glob
npm run typecheck           # tsc in client, server, tools, and for e2e/ and the config files

npm run security:allowlist  # .github/security-allowlist.json is valid and nothing has expired
npm run security:audit      # npm audit fails on a high or critical advisory the allowlist does not allow
```

Unit tests run with the device time zone fixed to `Europe/Berlin` (set in `client/vitest.config.ts`), so day and time-zone tests mean the same on every machine, including daylight-saving changes.

**Mutation testing** changes the code under test in small ways (a flipped condition, a removed call) and checks that a test fails for each change. Stryker mutates every `src/**/*.ts` of the client, the server and `tools/` by glob, so a new file is included without a config edit; each workspace's run fails below a score of 95 (client 97.5%, server 95.2%, tools 96.2%), and writes its HTML report to `reports/mutation/index.html` in the workspace. Left out, by glob: React components (`*.tsx`) and hooks (`client/src/**/use*.ts`), which only the end-to-end tests reach, the entry points (`main.tsx`, `server.ts`), test helpers, and the command-line wrappers of `tools/` (the reasons are in [docs/agents/testing.md](docs/agents/testing.md)).

Mutants that survive on purpose, because no input can tell them apart or no test can place the case, by file:

- **Closing a database** (`close()` of the Task, Event, List, Tag and Subtask stores): the tests keep using the database afterwards.
- **Races between two transactions**: `NoSubtaskError` thrown by `moveSubtask` and `moveSubtaskBy` when a sync deletes the Subtask between reading the order and writing its position; the check inside `clearList` that a Task is still in the List when it is cleared; that an outbox entry still exists when its push is confirmed or refused (`engine.ts`); the second look at "queued before sync" inside the transaction (`replica.ts`).
- **Defaults only the running app uses**: the sync engine's default clock (`engine.ts`) and the auto-sync's default window and document (`autoSync.ts`).
- **Equal either way**: the exact byte at which a batch is full, that the server's time is fed to the clock when pulling, the 100 KB below which a lone refused value is called the server's fault, that a refusal naming a change that was not sent fails the same way, that a queued edit is older than the change that beats it (`engine.ts`); `task.date !== null` and `task.time !== null` before a comparison that is false for `null` anyway (`lists.ts`, `reschedule.ts`, `buckets.ts`), the default `""` of a date in the order of Tasks (undated Tasks never share a Bucket with dated ones), `first <= today` where `first === today` gives Today either way (`buckets.ts`), `offsetDays <= 0` and `days >= 0` after the zero case is handled (`formatEvent.ts`), `day <= earliest` (`reschedule.ts`), a Task with neither Event nor Offset returned unchanged either way (`wholeLink`), the shape of an Event that is whole already (`eventStore.ts`), the text (`""`) that `withPendingTicks` puts where a tick's time is not known, and the `?.` and `{ remote: false }` that make the types honest where the value is always there.
- **Database upgrade**: the delete of the pull cursor under `oldVersion < 4` (the block for version 5 does it too, in the same upgrade) and `oldVersion < 5` (the upgrade function runs only below the new version).
- **The server**: the `database: "ready"` of the health answer (`SELECT 1` is always 1), the `^` and `.*` of the screen-address route (the API routes are answered before it), purging expired sign-in challenges (expired ones are refused whether or not they were purged), the guards in front of cookie and ceremony lookups that a missing value fails anyway, `.catch(() => null)` against `undefined` (both mean "not verified"), `clearCookie`'s default path, `PRAGMA foreign_keys` (node:sqlite turns them on), `mkdirSync` of `.` for `:memory:`, and the checks in `sync.ts` that a malformed value is refused twice over (`typeof value !== "object"` before the pattern checks, `limit === null` before `limit < 1`, `typeof raw === "string"`, the `isChange` filter after the check, `value !== undefined`).
- **`tools/`**: guards that make the types honest where a later check refuses the same input (the day pattern's anchors, a non-object report).

**Regression testing:** CI (`.github/workflows/ci.yml`) runs, as independent jobs on every pull request, every push to `main`, nightly and on demand: `typecheck`, `lint`, `unit` (coverage thresholds), `e2e`, `mutation` (client, server and tools in full), `docker` (build, smoke test, Trivy on the image and the Dockerfile), `npm audit` (allowlist, audit gate, signatures), `dependency review` (pull requests: high severity, copyleft licences), `codeql` and `secrets` (gitleaks over the whole history). ## Data model notes

- **Events** are stored in the shape of Outlook/iCalendar events (ADR-0002): start and end, an all-day flag, the time zone of timed Events (IANA name; all-day Events are floating), and `externalSource` / `externalId`, which are null for Events created in the app and will hold e.g. `"outlook"` and the Outlook id once Outlook sync arrives after v1. See `client/src/events/event.ts`.
- **Linked tasks** store their Event and an Offset in days, not a date (ADR-0003). Their date is always the Event's start date plus the Offset, so they follow when the Event moves. Rescheduling a Linked task changes its Offset, and writes `eventId`, `offsetDays` and `date` together.
- **`rescheduleCount`** on a Task counts its Reschedules (a Task getting its first date from the Inbox is scheduled, not rescheduled, so it doesn't count). It is stored and synced from v1 on and not shown yet (Smart hints come after v1). It is a field like any other, last write wins, so two devices rescheduling the same Task while apart can lose one increment; that is acceptable for a hint. Tasks saved before it existed read as 0. The name is a wire name: never rename it.

- **Lists, Projects and Tags** (`client/src/lists/`, `client/src/tags/`). A **Project** is a List with `isProject = true`; only the person's toggle sets it. A Task belongs to at most one List (`listId`, null = none) and has any number of Tags (`tagIds`, in the order they were added). The wire names `list`, `tag`, `name`, `isProject`, `listId` and `tagIds` are never to be renamed. Membership is a field on the member record, so Events can get a `listId` later (a Project showing its Events is not built yet).
- **`tagIds`** is one last-write-wins field, like `rescheduleCount`: two devices changing a Task's Tags while apart keep only the later set (one person on two devices; accepted). Each Tag change is one read-modify-write in a `Table.update`, so a sync landing meanwhile is never overwritten by a stale copy, and a change that changes nothing writes nothing.
- **Tag names**: typing a name reuses the live Tag of that name, ignoring case and the spaces around it (accents count: "Cafe" is not "Café"; `data/names.ts`). Two devices adding the same name while apart each make a Tag; both show, and filtering is per Tag id. Known limitation; Tags can't be renamed, merged or deleted yet.
- **Deleting a List** deletes its record and clears `listId` of its live Tasks (`useAppData.deleteList`). A reader also tolerates a `listId` that names no live List on this device (the List was deleted on another device while this one put a Task in it, or it has not arrived yet): the Task shows without a List everywhere (`liveList`). Lists have no Trash and no undo; the app asks first. Tasks in the Trash keep their `listId`. Known limitation: `clearList` writes `listId = null` under a new clock, so when another device, offline, had moved a Task from the deleted List to another List, the deletion wins once both sync and the Task ends up in no List (the move is lost on both devices; pinned by a test in `sync.test.ts`).
- **Subtasks** (`client/src/subtasks/`). A **Subtask** is a checklist entry of one Task: its own record type `subtask` with the fields `taskId`, `title`, `position`, `completedAt`, `createdAt` and `deletedAt`, which are wire names that are never to be renamed. There is one level only (a Subtask has no `subtaskId`, and `addSubtask` refuses the id of anything that is not a live Task) and no date or time (the type has no such field and the store no way to set one). The order within a Task is `position`, ascending, ties (two devices adding at once) by `createdAt`, then `id`; a new Subtask goes after the highest position, a moved one gets the midpoint of its new neighbours (so a move writes the `position` of that one Subtask), and when no midpoint is left (equal or adjacent numbers) the Task's Subtasks are renumbered 0 to n-1 in their new order. Adds and moves run one after the other in the store. A drop asks for an index (`moveSubtask`), an arrow key or a Move button for a number of places from where the Subtask is when the move runs (`moveSubtaskBy`): the screen shows a save a moment after the save, so a key held down outruns it, and an index worked out from what the screen shows would be stale. Each field syncs on its own, so a rename on one device and a tick on another both survive; two devices reordering the same Task while apart each write `position` of the Subtasks they moved, and the later write per Subtask wins, so the order that results can be one neither device made (accepted, like `tagIds`). **Deleting a Task does not touch its Subtasks**: they stay live records whose Task is in the Trash, the screens show a Task's Subtasks only for a live Task, and restoring the Task brings them back as they were. Deleting a Subtask is a tombstone like any other (`deleteSubtask` says whether it deleted one, so that the undo toast is shown only for a Subtask this delete removed; the answer comes from `Table.delete`, which looks and writes in one transaction, so a Subtask that another tab deleted at the same moment, or that a sync pull deleted just before, is not offered an undo; one that another device deleted and that has not reached this device yet still is, because this device cannot know it); Subtasks are **not in the Trash screen on their own**: the undo toast (5 seconds) is the only way to bring one back. A Subtask that arrived with no `taskId` or no `title` yet is left out of `listSubtasks()`. **Subtasks never count toward Progress**: they are not Tasks, live in their own store, and `arrangeHome`, `listProgress` and `eventProgress` read Tasks only; a Task row's "3/5" is a separate figure (`subtaskCounts`). Ticking the last open Subtask of an open Task only offers to Complete the Task (`offersCompletion`, asked of the Subtasks with the ticks still being saved, `withPendingTicks`); nothing Completes it by itself. The database upgrade to version 5 adds the `subtasks` store and resets the pull cursor.
- Tasks saved before Lists existed are not rewritten by the database upgrade (version 4 adds the `lists` and `tags` stores): they read with `listId: null` and `tagIds: []` and get clocks only when first changed.

## Sync

Tasks, Events, Lists, Tags and Subtasks live in IndexedDB on each device and sync through the server (ADR-0004), so a Task added on the phone shows on the desktop. It only works signed in; the server refuses sync requests without a session.

**When it runs:** when the app starts signed in, when the connection comes back, when the app returns to the foreground, about 2 seconds after each local change, and once a minute while the app is visible. The home screen footer shows the outcome (*Synced 14:32*, *Syncing…*, *Offline · last synced 14:32*, *Sync failed*, *Some changes could not be synced*, *Signed out – sign in to sync*) and has a *Sync now* button. *Syncing…* shows only for a run started with that button; background runs leave the line alone until they end, and the line is not a live region (a hidden one announces it to screen readers only when it means something new). When the server says the session is gone, the app asks it again and shows the sign-in screen; local data stays.

**The protocol:** the unit is a **Change**: one field of one record (`type`, `id`, `field`, `value`, `hlc`). Every field except `id` syncs on its own, so a title edited on one device and a date edited on another both survive; when the same field was edited on both, the later change wins on every device. All fields a store operation names (e.g. linking a Task: `eventId`, `offsetDays`, `date`) share one clock and are all sent, also those whose value stays the same, so they win or lose together. A store operation reads, changes and writes the record in one IndexedDB transaction (`Table.update`), so a sync that lands meanwhile is never overwritten by a stale copy; the Event form and the Edit sheet of a List send only the fields the person changed, except that a change to *when* the Event is (all-day, start and end date, start and end time, time zone) sends all six of those fields together, so that two devices' competing edits of the time never mix into an Event neither made. Each device keeps an *outbox* of changes the server hasn't confirmed (a newer edit of a field replaces the older queued one) and, per record, the clock of every field (`fieldClocks` store). A sync pushes the outbox to `POST /api/sync/push`, then pulls `GET /api/sync/pull?after=<cursor>` page by page and applies each Change whose clock is later than the local one. The server keeps only the winning value per field (table `sync_fields`, per owner) and knows no record types.

**Large and refused pushes:** the app caps what a person can enter (titles and locations 200 characters, notes 10,000; the inputs stop at the cap and `client/src/data/limits.ts` has the numbers), so no single value comes near the server's limit. A push is split into requests of at most 500 changes and about 400 KB (the server takes 1 MB, so only a lone value, which gets a request of its own however big, can be refused as too big; behind a proxy with a limit below 400 KB, lower `batchBytes` in `engine.ts`). The client sets a change aside only when it is certain that the change itself is bad: our server answers a malformed batch with `400 { index }` naming the first malformed change (that one is set aside and the rest is sent in a new request), and a lone value over 100 KB refused with 413 is set aside too. Any other refusal says the server is unwell, not the changes: a 400 that names no change (a proxy, a captive portal, a server bug), a 413 for anything smaller or for several changes, or a 5xx ends the push after that one request, nothing is set aside, the status is *Sync failed*, and the next sync sends everything. A set-aside change stays in the outbox, unsent, and the status line says *Some changes could not be synced*; it is tried again an hour after it was set aside (the check runs at every push, and the mark survives a restart of the app), and a newer edit of the same field (e.g. a shorter note) replaces it and is sent at once. Until then the value is on this device only. A push that fails for another reason does not keep the pull from running.

**Deleting** is a field too: `deletedAt` (the time, or `null`) is an ordinary last-write-wins field, and the record stays stored as a tombstone. Edits to other fields of a deleted record merge but never un-delete it. The stores' `list…` functions leave deleted records out.

**The Trash** builds on the tombstones: a deleted Task shows in the Trash (`#/trash`, linked from the home footer until Settings exist) for 30 × 24 hours, newest deletion first. *Restore* is a later write of `deletedAt` itself (`null`, one field, one outbox entry, `Table.restore`), so it beats the older delete on every device, like any later edit of a field; a delete made after the restore wins again. A Task deleted 30 days ago or longer is no longer listed and can't be restored, but its tombstone stays stored (it is what keeps sync from bringing the Task back from another device), and tombstones are never compacted. The Trash's rules are in `client/src/tasks/trash.ts`.

**The clock** is a hybrid logical clock ([ADR-0010](docs/adr/0010-hybrid-logical-clock-orders-sync-changes.md), `client/src/sync/hlc.ts`): wall time, a counter and the device id as fixed-width text, so string order is time order. A device moves its clock past everything it sees, including the server's time in each answer, so an edit made after seeing another device's change wins even on a slow clock. A device whose clock runs far ahead wins concurrent edits until real time catches up.

**Data from before sync:** Tasks and Events saved by earlier versions get clocks and outbox entries (and `deletedAt: null`) once per record type, the first time its store is opened or the engine runs (a flag in the `syncInfo` store says it is done), so they reach the server too.

**Known limitations:** a Change of a record type this version doesn't know (from a newer app on another device) is skipped, and the cursor moves on, so an older app never receives it later by itself: the database upgrade that adds a record type resets the pull cursor (step 6 of "Adding a record type"), so a device that updates re-reads the feed once and gets what it skipped (this also needs the older app to have saved its Tasks' unknown fields, which it does). A record can be stored in part for a while, with placeholder values for the fields that have not arrived: when its Changes are split across two pull pages and the sync stops between them, when the other device's push was cut off between two of its batches (the outbox is sent in key order, so a batch can end inside a record), or when a field of it was set aside on the other device (that field arrives only once it is sent). Until the rest arrives, the lists leave out an Event that has no title, start date or end date yet (its Linked tasks show as undated, in the Inbox), screens read an Event whose time fields are incomplete as an all-day Event, and a Linked task missing its Event or Offset reads as a Task without an Event. Tombstones are never compacted. Another tab upgrading the database makes this tab's connections close; the app then shows a *Reload* screen, since nothing could be saved in this tab any more.

### Adding a record type

Reminders and the like need no change in the sync engine or the server (Lists, Tags and Subtasks are the examples to follow: `client/src/lists/listStore.ts`, `client/src/tags/tagStore.ts`, `client/src/subtasks/subtaskStore.ts`, database versions 4 and 5):

1. Give the record `id` and `deletedAt: string | null` (the tombstone) next to its other fields; the other fields are JSON values.
2. Add its object store in `openAppDb` (`client/src/data/database.ts`) in a **new** database version (`if (oldVersion < 6) …` for the next one), and add it to `AppDb`.
3. Define its `RecordType` next to its store: `type` (the wire name), `storeName`, and `withDefaults`, which fills fields missing from records saved by older versions or built from partly arrived Changes (see `taskRecordType`).
4. Register it in the list in `client/src/sync/recordTypes.ts`.
5. In its store, open the table with `openTable(db, recordType, now)` and write only through it (`get`, `list`, `put` for a new record only (it throws when the id is taken), `update` to change a stored one, `delete`), never with `db.put`: the table stamps the clock and fills the outbox. Change a stored record with `update` (it reads and writes in one transaction); `put` can't replace a record, so a stale copy can't overwrite a sync. Where a record must not be made twice (a Tag of the same name), `findOrPut` looks and saves in one transaction.
6. In the same database upgrade, reset the pull cursor: `upgradeTransaction.objectStore("syncInfo").delete("cursor")` (see versions 4 and 5). A device on the previous version skips Changes of the new type and moves its cursor past them, so without the reset it would never receive them after it updates; the one extra full pull is safe, because a Change is applied only when its clock beats the field's local clock. Test it like `database.test.ts` and the "synced on the version without Subtasks" test in `sync.test.ts` (the one for version 4 is "synced on the version without Lists and Tags").

Never rename a `type` or a field once shipped; the server and other devices know them by name. To rename, add a new field and stop using the old one. A type and its fields must also match the server's checks: `type` is letters starting lowercase (up to 40), a field is letters and digits starting with a letter (up to 64), and `id` is never a field. A unit test (`client/src/sync/recordTypes.test.ts`) checks every registered type against copies of the server's patterns (`typePattern`, `fieldPattern` in `server/src/sync.ts`), so a field such as `due_date` fails there, not silently on a device; change the patterns in both places.

## Translations

Every UI text lives in `client/src/i18n/en.json` and `client/src/i18n/de.json`. Add a key to both files; a unit test fails if the files do not have the same keys (a key missing in German also fails the typecheck). Placeholders use `{name}`, e.g. `"task.completeNamed": "Complete {title}"`. In code, get texts with `const { t } = useI18n()` and `t("task.add")`. The German wording follows the *German UI* labels in [CONTEXT.md](CONTEXT.md).

## Build

```sh
npm run build         # client/dist (PWA incl. service worker) and server/dist
docker compose build  # production image
```

Server configuration (environment variables):

| Variable | Default | |
| --- | --- | --- |
| `PORT` | `3000` | HTTP port |
| `CLIENT_DIR` | `client/dist` | built PWA to serve |
| `DATABASE_FILE` | `data/grilled-heads-up.sqlite` | SQLite file, created if missing; `:memory:` for a throwaway database (tests) |
| `ORIGIN` | `http://localhost:$PORT` (plus `http://localhost:5173` unless `NODE_ENV=production`) | the address(es) the app is opened at, comma-separated, e.g. `https://heads-up.example.com`. Passkeys are bound to the first one's host name; with `https:` the session cookie is `Secure` |
